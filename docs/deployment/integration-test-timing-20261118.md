## 候选优化与必须保留的检查

1. **减少重复建库初始化工作，先做隔离对照。** 对普通业务用例可评估按固定迁移和模型指纹建立只读初始模板，再为每个夹具创建独立数据库。迁移、空库初始化、权限边界、故障注入、超时和迁移回执测试仍走原始数据库与真实迁移路径；任何复用都不能共享可变业务数据。必须验证模板失效条件、全量用例覆盖、跨夹具污染和清理，再判断收益。
2. **调查销毁与连接池生命周期。** `PostgresDatabase.DisposeAsync` 当前调用全局 `NpgsqlConnection.ClearAllPools()` 后执行 `DROP DATABASE ... WITH (FORCE)`。应区分这两个动作的直接耗时，并测量是否影响其他并发夹具的连接复用；不能只根据源码就认定全局清池是主因。若改为按所有者回收，必须覆盖不同连接串、后台任务、失败中断及最终资源为零；不取消销毁，也不降低数据库持久性设置。
3. **分解HTTP启动和登录。** 区分CSRF读取、真实登录请求、数据库/Redis交互和密码验证后，再决定是否优化夹具准备。认证、安全、权限测试必须继续真实登录；不得直接注入会话或关闭登录保护来取绿。
4. **再考虑CI分片。** 若仍需降低等待，可对不同测试集合使用独立数据库/Redis资源并行运行。必须证明所有2254项恰好覆盖一次、零跳过、每片失败都会使既有必需检查失败，并保留原总门槛；先做固定输入对照，不直接扩大单runner内部并发。
5. **构建缓存作为次要收益。** 即便理想化移除本轮所有测试外区间，也只节省约134秒；实际缓存只能覆盖其中一部分。缓存需绑定锁文件、SDK、源码及工具版本，不能把较旧构建当作当前修订的验证。

本轮只给出测量和候选，没有宣称任何候选已经提速或适合生产。旧治理运行链、G14、通知现场资格和历史CI失败Unknown与本分析分开，旧资料及原始失败日志继续保留。原始日志、逐阶段JSON、插桩差异和哈希清单存于本机私有证据目录 `deliverables/status-and-integration-profile-20261118/`。
