UTM 是**验证平台候选**，不是已通过的产品存储适配器。固定容量文件系统可以作为卷组的上限候选，但必须证明没有卷落在该文件系统之外，并实测边界；它不天然提供每卷独立配额，也不能证明独立防回滚见证。

## 候选拓扑和约束

新建且仅属于新 owner 的 UTM Linux 虚拟机使用独立 guest 内核、独立 Docker daemon、独立 guest 系统盘和另一块用于目标卷组的固定容量虚拟块设备。目标设备在 guest 内格式化为 ext4，挂载到该独立 daemon 的 `local` 卷根；具体挂载兼容性和支持状态待验证，不能假设 Docker 会接受这种配置。目标卷及其所有实际写入路径必须逐个证明归属于该设备。daemon 元数据、镜像／containerd 层、日志、只读输入、宿主证据与目标卷配额分别计量；Docker 版本可能将镜像和快照放在其他根目录，因此不能只看 `data-root`。

测试初值：专用 guest 系统盘不大于 8 GiB、目标设备容量 512 MiB、2 vCPU、2 GiB 内存、宿主独立证据上限 128 MiB；这些不是生产规格。执行前宿主空闲空间在预留全部计划最大支出后仍须至少 20 GiB，并配置有界日志与监测；不能从逻辑文件大小推断已预留物理空间。系统盘、目标盘和只读介质都必须独立限制大小，guest 不能加载或挂载主机目录、宿主 Docker socket、现有 VM 磁盘或外部网络。

虚拟磁盘可稀疏、共享底层空间或支持写时复制。拟使用固定大小、无 backing chain 的虚拟磁盘并核验所在文件系统的实际分配与可用空间；若无法验证物理预留、持续空闲水位或设备身份，则不得执行写满。即使通过这些检查，仍需区分共享物理介质、快照、压缩、薄置备等风险，不能承诺底层故障隔离。不得将 UTM 软件自带的动态库误当作可调用命令。

控制路径需在每阶段绑定：新 owner → UTM 实例及配置 → 虚拟磁盘文件及身份 → guest 块设备与文件系统 UUID／挂载点 → daemon 身份与 Unix socket → 全部目标卷身份与实际挂载 → 预算与证据。daemon 必须只存在于该 guest；运行产品命令时须防止继承宿主 Docker context／socket。任何环节缺失、路径替换、挂载消失、资源超限或 daemon 指向不明均立即阻断。

## 分阶段资格

1. **资源与介质资格**：完成只读盘点、预留计算、guest 离线介质和工具身份核验、全新 owner 及确切操作清单。UTM 可能写入应用自身的注册及缓存位置：须事先确认具体路径、权限与影响；若不能限定，不能创建／启动。
2. **文件系统试验**：未来经单独授权后，仅在新 guest 的专用设备上写入实际数据、验证上限及错误、正常关机后冷启动并核对数据与身份。独立结果只证明该测试设备的行为。
3. **Docker 卷组试验**：若离线 Docker 及最小固定镜像均已验证，验证两个测试具名卷的设备映射、合计上限和重启数据；身份或挂载异常时由实验自身停止。Docker 服务或卷无法在空间耗尽后启动时记录失败，不释放现场来伪造成功。此试验不证明所有产品卷或产品阻断已通过。
4. **产品适配与恢复**：需要另行设计和实现可信 verifier，并对当前源码、全部所需离线依赖、真实 manifest 的全部动态卷、三阶段的身份与错误阻断、冷恢复真实业务内容开展完整验证。文件系统试验成功不会自动通过这一阶段；独立连续性见证与 source→clone 来源绑定仍另有门禁。

一个测试目标不能复用历史失败或未知现场。每次尝试使用全新 owner，预先持久化意图；失败、超时、宿主空间风险或身份不符时停止并保留原始证据，不自动重试、回滚、清理或覆盖。受限证据回执是本地观察，不是防回滚签名。
