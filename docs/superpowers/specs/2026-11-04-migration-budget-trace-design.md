# 迁移预算、校验追溯与旧写入者隔离设计草案

## 1. 背景与目标

受控 Migrator 已在一个事务内执行结构检查、.NET 通知校验与升级；独立 SQL 对含通知数据的待升级历史库保护性阻断。当前单次锁等待最多五秒，但迁移总耗时、输入体量和数据库端资源没有完整预算；一次失败回滚后，事务内无法留下失败记录。事务锁在提交后释放，不能证明旧进程随后仍被隔离。

目标是限定迁移工作量和停止行为、持久化可区分的校验／迁移结果，并在独立 PostgreSQL 中检查停写措施在迁移前、迁移中、提交后和异常恢复后的状态。实际环境切换及旧进程操作不在本次范围。

## 2. 追溯存储方案

### A：库内成功回执＋独立持久证据目录（已确认）

- 为每次尝试生成随机 ID。开始前将有限大小、脱敏的 `Started` 记录写入已配置的持久目录，并验证文件和目录的持久写入能力；无法建立记录则不开始迁移。记录不能覆盖、自动删除或重用已有证据。
- 在与迁移相同的数据库事务内写入成功回执；只有事务提交后，数据库回执才表示此次事务确已提交。随后在证据目录记录完成状态。失败或受控取消在回滚后另行记录，原始错误仅保存不包含连接信息、Secret 和通知内容的分类与必要定位信息。
- 数据库提交与外部记录不构成分布式原子事务。崩溃、超时或存储写入失败时保留 `Unknown`／`待核对`，不得推断失败并自动重跑。按尝试 ID 查询数据库回执与独立证据，区分 `Committed`、`Failed` 与仍然未知的情况；数据库不可达、身份无法核验、可能恢复到旧备份或查不到回执，均不足以证明未提交。只有有可靠证据确认未提交或已回滚时才能记 `Failed`。
- 推荐新增一个独立的前向迁移建立有界的迁移回执表，对普通更新、删除和截断设保护；不改已应用迁移或旧指纹。数据库拥有者、超级用户、整体备份回退和底层文件替换仍可改变证据，不能称为不可篡改或独立可信见证。另一种实现是复用现有 `audit_logs`，但其留存及修改权限需先证明满足同一合同。
- 持久目录须由部署方配置并具备私有权限、剩余空间与明确的安全挂载；不能把容器 `/tmp` 当成持久证据。单条记录及总目录配额需要固定上限；配额不足时迁移前阻断，不自动清理。持久目录可与数据库处于不同事务域，但物理故障域独立性需实际核验，不能由路径名称推断。
- 现有纯 SQL 仍可作为符合条件的独立入口；它无法独自在自身回滚的事务中保存失败记录。提供受控执行方式采集外部证据时必须保留原 SQL 独立入口合同；直接运行的失败结果如果没有独立采集，应显示为追溯不完整，不能记为有持久证据。若交付门禁要求所有入口的失败都强制持久化，需另行确定是否改变这一合同。

### B：仅目标库保存成功回执

实现较简单、无独立卷要求，但回滚后的失败只能依赖现有运行日志，无法保证失败结果持久化；因此不能完整满足对成功和失败均可追溯的目标。

## 3. 回执内容与边界

回执记录版本、尝试 ID、实际入口、来源／目标迁移范围、数据库身份（能够核验时）、历史结构和迁移清单摘要、通知校验结论、已处理记录数量／字节、预算及命中原因、固定历史 SQL 操作哈希、可核验的构建／程序集身份、时间和提交状态。

不记录通知正文、URL、密钥引用、密码、连接字符串或数据库错误详情。摘要及程序集哈希只能标识被观察的内容，不自动证明构建来源、输入完整性或存储防回滚。空库、没有通知数据、纯 SQL 阻断、未完成校验和已通过校验必须分别表达，不能将 `NotApplicable` 或 `Unknown` 写成 `Passed`。

现有来源采集在迁移账号无法读取集群身份时允许返回未知；新回执不能凭数据库名称或调用方提供的标签声称身份已核验。若对账缺少足够身份和恢复连续性证据，应保持未知，不为获取证据而默认授予超级用户权限。

当前命令在迁移事务提交后才执行可选的 `--bootstrap` 和 `--seed-catalog`。本稿的 15 分钟建议仅指迁移事务；命令结果应分别记录迁移、管理员初始化和权限目录种子的状态。迁移提交后初始化失败时，应显示“迁移已提交、后续步骤失败／未知”，不得声称整体回滚或把迁移回执当作整个命令成功。

## 4. 资源预算提案（数值作为隔离测试初值）

| 范围 | 建议默认值 | 建议行为和限制 |
| --- | --- | --- |
| 整个迁移事务 | 15 分钟 | 配置范围建议 1–60 分钟；只允许在有界范围内调整。达到时间后取消／终止并核实回滚；超时不是“回滚已完成”的证明。 |
| 单次锁等待 | 不超过 5 秒 | 保留已有更短限制；超时停止，不自动重试。 |
| 单条告警通知规则 | 16 KiB | 对齐现有 .NET 校验器的 UTF-8 字节上限；在传输至 .NET 前识别超限，测试不同字符和 PostgreSQL JSONB 表示。 |
| 单条通知设置 | 建议 64 KiB | 属于迁移资源上限，不等同于产品合法性规则；超限报告预算原因，保留原值。需先证明对已有有效历史数据的兼容，不能直接采用接口 8 KiB 限制。 |
| 告警规则数量／累计读取 | 建议 100,000 条／64 MiB | 逐条处理并限制总量；超出时保护性停止且不删除数据。应在有界配置及实际数据统计依据下调整，不能假设该默认值覆盖所有客户。 |

预算要作用于数据库锁、SQL 执行和 .NET 数据读取／处理的整个迁移窗口；配置缺失、非法或超出允许范围时不得静默放宽。PostgreSQL 17 的事务超时可作为服务器端边界的一部分，但与应用取消配合时仍需分别验证连接断开、事务回滚和锁释放。

`work_mem`、单条 SQL 超时或客户端读取上限都不能严格约束 PostgreSQL 对压缩 JSON 解压、索引构建、回滚及所有临时文件的内存／磁盘峰值。迁移前还需核验数据库服务器的资源配额、空闲空间与维护窗口；不具备证据时阻断或保留未验收状态。上述数字是方案提议，不是已测得的生产容量或性能承诺。

## 5. 隔离验证

1. 仅使用已授权的独立 PostgreSQL owner 和一次性数据／角色；确认身份后建立原始数据摘要及迁移历史。角色和资源由本测试唯一命名，异常时保留证据，不触碰既有保留库、其他容器或 4192。
2. 对两种入口分别测试可连接的旧写入者会阻断迁移；禁用旧登录不会关闭已有连接，必须处理完该连接才能继续。同步屏障观察迁移期间及提交后的旧账号登录／写入拒绝，并核对迁移数据和历史。
3. 在一次性环境模拟迁移取消、进程中止、超时及重入，核对连接关闭、回滚完成、旧账号仍被隔离、成功回执和外部证据的对应关系；数据库或证据不可判定时保持 `Unknown`。
4. 验证超限边界、Unicode／压缩大值、规则行数和累计字节预算、证据卷不可用或配额耗尽、成功提交与外部完成记录之间中断，以及从未知状态对账。保留首次失败和全部原始日志。
5. 测试不等同于真实环境中的身份清单、代理连接、数据库拥有者、管理员行为、持久卷拓扑或外部可信见证验收；这些仍是后续环境门禁。
6. 实际受控迁移器在显式事务中调用来源捕获。独立审查发现其捕获 `pg_control_system()` 的权限异常后会继续使用已失败事务；一次性数据库与真实受控入口测试均已复现。候选已用保存点修复，受限角色测试确认迁移完成且来源保持 `Unknown`，未创建虚构回执。查询被取消、恢复超时、事务登记失败、外部事务和 ambient 事务均须单独验证；不能以无外层事务的旧测试代替真实受控入口验证。
7. 现有候选先持有 provider 事务，再通过 EF `UseTransactionAsync` 登记，以确保登记失败时能够释放自有事务而不影响调用方事务。这会产生 EF 的 `TransactionUsed` 回调，而不是原 `TransactionStarting`／`TransactionStarted` 回调；仓库生产代码未发现相关拦截器，但外部扩展是否依赖旧回调尚需核验，不应声称语义完全不变。
