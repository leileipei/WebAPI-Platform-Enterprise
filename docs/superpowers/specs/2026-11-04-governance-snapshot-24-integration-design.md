# 治理快照 2.4 与主线集成设计

日期：2026-11-04。状态：**待设计审阅；不是已实现或已验收的协议。**

## 1. 目标、依据与边界

在保留当前主线业务的前提下，将治理工作区中可验证的应用、凭证、路由与方法授权、安全账本、凭证轮换等能力整合进主线。通知恢复分支一并检查，但只合入适用于当前产品且通过验证的内容。

本设计依据的输入是主线 `369139df0fde68c8309849038e7f7eb7c58955a1`，治理工作区基准 `40759aac50f1a6281223b0ec0d45d58e6fb44cb5` 及其经清单核验的未提交工作文件；通知恢复分支为 `cf41823b9a7bcac7f0ef2195b66c4efa058883ac`。治理工作区的未提交文件不是一个已经完成的 Git 提交，后续集成必须按内容清单核对；如果输入发生变化，重新检查差异及本设计的适用性。

已由用户选择：

1. 同时检查治理工作区和通知恢复分支，只合并通过验证的内容。
2. 新增治理快照 2.4，保留既有网络策略 2.3，并严格检查节点能力和回滚。
3. 普通轮换继续显式撤销旧凭证；仅管理员明确选择并确认正式轮换，才启用硬截止自动撤旧。

本设计需要明确接受的运行约束：数据库切换需旧控制面／Worker 停写；旧控制面不能给新网关提供可信租约，因此不支持先升级网关并继续依赖旧控制面的受保护流量。新网关即使处理旧网络 2.3，也依赖新控制面签发的有效安全状态；签发故障可能产生 503。旧环境资料不足时需先隔离旧入口，不能自动判为安全。正式轮换硬截止可能在新凭证未验证时中断调用，安全状态故障还可能影响同环境其他受保护流量。上述均为待审阅设计约束，不代表已经在现有环境执行。

保护现有工作区、G14 等历史失败及原始证据、已有服务、账号和数据；不得把历史失败改写为通过。第 2 包性能验收、G14 正式验收和本次产品集成分别记账。本文不授权部署、推送或改动现有运行环境。固定结果、隔离环境及实际运行验证都须与原始证据区分。

源码对照及局部检查见同目录《合并检查报告》、`snapshot-conflict-evidence.json`、`migration-inventory.json`、`merge-simulation.json`。当前仅完成静态核对与报告中的局部前端检查，尚未完成本设计的合并、后端构建、数据库迁移及双网关验收。

## 2. 两类待处理内容

### 2.1 治理工作区

经检查的 433 项产品源码、测试、脚本及非证据文档中，62 个已跟踪文件两侧均有变更，三方文本模拟有 46 个文件冲突；另有 3 个同路径新增文件内容不同。不能以整文件选择某一侧代替语义整合，也不能将 74,667 个未跟踪文件批量纳入提交。先建立精确清单，区分产品内容、生成物、迁移、历史研究、失败证据及秘密材料；只将产品所需且审查通过的文件用于隔离候选。

特别保留主线的 CORS、IP、Transform、JSON 正文映射、JWT、重试、缓存、首次改密、Credential 统计、风险确认和跨环境发布；同时纳入经验证的治理环境绑定、路由方法授权、安全账本和正式轮换。三个同名轮换前端文件要合并公开接口，不得删除主线既有导出。

### 2.2 通知恢复分支

该分支以较早产品版本为基础，是旧版本读取新通知设置的只读降级恢复工件。主线现有交付记录已将它保留为独立工件；直接并入会遇到四处冲突，且存在重复测试／重试路由、旧字段投影与当前 Worker 行为不匹配的风险。静态检查不足以证明这些旧提交适合当前主线，因此保留原分支及恢复说明，不通过空合并或偏向某一侧的合并制造“已并入”的假象。若后续发现当前主线确需其某一独立能力，应按当前九字段合同、Worker 实际行为和接口测试单独实现与审查。

## 3. 快照协议与历史兼容

### 3.1 当前冲突

主线用 2.3 表示 CORS／IP／Transform，治理工作区用相同版本表示带安全账本身份的治理快照。主线解析器可忽略未知字段，旧节点只声明 2.3 并不能证明其执行治理规则；治理侧则要求所有 2.3 具有治理字段。上述是源码层面的不兼容风险，本次未证明现有运行环境中一定存在两种历史快照。

| 输入 | 新控制面和新网关的规则 | 在严格治理环境中激活 |
| --- | --- | --- |
| 已有 2.0／2.1／2.2 | 保留原协议的解析、业务与发布合同；不得擅自增加治理含义 | 不可作为满足更高治理下限的版本 |
| 主线网络 2.3 | 保留原字节、网络策略与现有非严格环境行为；不能因版本号认定具备治理能力 | 不可，仅可用于只读历史查看或按本节规则重建候选 |
| 治理侧历史 2.3 | 仅在原始来源、字段和安全账本身份均可证明时作为治理方言解析；原始内容和身份不可改写 | 仅当当前环境安全下限、账本、节点能力和发布审批均允许时才可能投递；默认以当前安全状态重建 2.4 候选 |
| 新治理 2.4 | 网络策略与完整治理字段共同校验，要求 2.4 与安全账本能力 | 通过当前安全下限、账本、租约和所有发布门禁后允许 |

所有历史快照、发布记录、原始字节、环境与版本身份、大小及 SHA-256 保持不变。原始快照的哈希校验不等于数字签名；本设计保留现有快照 Hash 合同，安全 checkpoint／节点租约仍使用各自的签名和校验，不声称快照本身已经签名。

### 3.2 2.3 方言判定与安全下限

1. 在控制面读取发布工件时，同时校验受保护存储中的环境、配置版本、原始大小与 Hash，并结合可信的发布来源、环境安全账本、迁移记录和高水位判定上下文。单靠快照自称的版本、字段缺失、可变备注或“查不到一行”不能证明环境非严格。
2. 历史原始字节中四个顶层治理字段全部缺失、且嵌套结构不含保留治理字段时，只有经独立环境证据证明仍为旧非严格状态，才按网络 2.3 原行为处理。四字段完整仅是治理候选的必要条件；还须通过治理 wire 校验及独立可信账本验证。四字段部分出现、嵌套安全字段混入旧方言、重复或大小写冲突的安全属性、来源不明、账本矛盾或状态无法确定时，拒绝发布／激活并给出可诊断原因。
3. 为旧环境建立明确的初始化／兼容状态，迁移前检查已有安全表、事件、签名 checkpoint、高水位及已知发布历史；无法证明无治理历史的环境保持待核验，不能因新增表为空而自动放宽。迁移结果必须持久化，重启后不得凭缺行降级。
4. 治理账本状态中的 `minimumSnapshotSchema=2.3` 表示**治理**安全下限，不等同于主线网络 2.3。保留原哈希链事件、已签名 checkpoint 和解释，以安全能力语义比较而不是只比较版本字符串。若后续将安全下限推进到 2.4，追加新的合法事件，不重写旧事件或伪造签名。账本事件自身的哈希链校验与 checkpoint／租约签名校验分别进行。
5. 安全模式由当前可信账本和环境状态决定，而不是由待加载快照决定。治理字段中的 generation／epoch／最低协议／环境凭证要求须与可信账本及允许的历史关系一致；撤销墓碑、代际、epoch、节点租约和本地持久化高水位不可回退。账本不完整、签名或持久化失败、旧租约、实例身份不匹配、未知状态均不放行受保护请求。
6. 保留主线历史允许的**非安全**未知字段兼容性，以真实历史样本核查；安全保留字段按大小写及重复键检查，不能借旧版宽松反序列化隐藏治理字段。兼容性测试必须检查既有可读取样本，也要检查变体、重复键、半套字段及恶意混合字段。

**旧环境进入非严格兼容态的具体条件。** 对升级前已存在的环境，必须同时满足以下条件，缺一则为 `Unknown`，停止该环境的旧快照投递和 2.4／严格切换并提示补证，不能自动认定为非严格：

- 迁移前的数据库身份、环境 ID、主线迁移历史及实际结构与受支持的主线基线相符，没有治理草稿迁移 ID、治理安全账本／墓碑及其专属结构；这只是必要条件，不单凭空表推断。
- 由部署负责人提供自环境初始化以来可核验的版本／部署清单，能将控制面与网关的运行身份、源提交／镜像摘要、持久数据和环境 ID 关联到不包含治理写路径的已知主线版本；核对已知恢复、克隆及节点替换记录。存在来源断档或无法排除曾运行治理代码时不通过。清单 Hash 只用于固定内容，不宣称其本身是签名或硬件证明。
- 在受控停写的范围内核对该环境全部已知网关的持久安全 checkpoint／高水位及恢复资料；任何发现、无法读取或与数据库不一致均不得认定为旧非严格。对已发布环境还须核对当前发布记录、原始快照大小／Hash、配置版本及节点运行身份；尚未发布的环境须有可核验的未发布记录，不能靠缺文件猜测。
- 具有该环境 `environment.write` 和 `gateway.config.read` 的管理员查看上述证据、范围、风险及缺口后，显式确认并填写理由；服务端在环境锁和预览指纹下复验并保存环境级 `VerifiedLegacyNetwork` 结论、依据的证据摘要、确认人／时间及审计记录。该记录是受权限控制的运行状态，不声称是外部密码学证明，也不保存秘密。预览后证据或环境发生变化必须重审。

真正的新空库、新建环境可在创建事务中记录 `FreshNonStrict`，不能以此给未知旧环境补记；已存在可信治理账本的环境走账本验证，不走旧环境证明。兼容状态只能向治理状态加强；一旦观察到治理账本、已签名 checkpoint、严格下限或更高安全水位，就不能回写为非严格。受支持的旧环境因此可以保留主线 2.3 行为；资料不全的现有环境会被阻断，这是本设计明确的适用限制，不能作为所有现有环境已验证兼容的声明。

网关不直接信任管理员的浏览器选择或未签名标志。对已证明的非严格环境，新控制面在初始化安全账本时绑定上述环境级结论，并向已认证的当前节点实例签发新鲜、匹配环境／实例的 checkpoint 与租约；新网关验证签名、下限及本地高水位后，才可按网络 2.3 非严格合同放行受保护请求。签发端必须验证结论尚有效，不能对 `Unknown` 或已治理状态签发旧兼容租约。新实例、重启或签名／签发不可用时不能复用上次进程的租约；无法取得可信状态则受保护请求返回 503。旧控制面无法签发这个状态，因此不支持在旧控制面上启动新网关来继续受保护业务。

### 3.3 2.4 线格式

2.4 以主线的八个顶层字段 `schemaVersion`、`environmentId`、`configVersion`、`generatedAt`、`routes`、`clusters`、`policies`、`applications` 为基础，并要求 `requiredSecurityGeneration`、`requiredSecurityEpoch`、`requireEnvironmentCredentials`、`minimumSnapshotSchema` 四字段完整存在且类型正确。网络策略及主线已支持的认证、缓存、重试、路径／查询／Header／JSON 映射合同均保留。

路由包含环境及授权修订；应用包含环境；凭证明确 `bindingMode` 和 `environmentId`，授权包含环境、`mode` 和 `routeMethods`。`EnvironmentBound` 的环境必须匹配；允许的 `LegacyGlobal` 必须明确写出 `environmentId: null`，不能因默认序列化忽略 null 而制造“要求字段存在但实际缺失”的格式。`LegacyApi` 授权仅在当前安全策略允许时可用；`RouteMethod` 的路由必须属于相应 API，方法须合法，只有授权修订与路由当前修订相等且方法仍在路由允许集合时才放行。保留治理侧的失效历史：修订不相等的授权可以随快照存在，但该授权明确拒绝请求；不因它过期而自动拓宽权限或一律阻断整个发布。严格治理下限禁止把旧 API 级授权悄悄恢复为更宽权限。是否允许全局凭证以可信账本的环境凭证要求为准，不能只看快照自述。

采用既有规范序列化、排序、16 MiB 上限、原始字节 Hash 及不可变发布包合同；2.4 引入的显式 null 仅针对新协议，不改写 2.0—2.3 字节。校验空集合、重复 ID、跨环境引用、非法模式、认证方式与策略组合、字段类型和长度，完整范围以双方既有校验与测试的并集为底线。网络策略与治理字段合并后的样本必须同时通过两侧业务约束。

首次从非治理快照切换到 2.4 时，必须为全部仍在运行的路由／授权建立可信冻结身份；沿用治理侧“全量冻结或拒绝”的安全规则，不为未纳入候选的路由编造授权修订。未选择的业务 API、Cluster 和策略仍应保留其正确运行配置；若无法无损冻结，应要求按既有流程补齐发布范围，而非删除或放宽授权。

## 4. 节点、发布与回滚

### 4.1 节点能力

新节点明确声明受当前节点实例绑定的 `supportedSnapshotSchemas`（含支持的 2.0—2.4）及 `security-ledger-v1`；版本数组的校验上限同步从 4 调整为至少 5。声明通过现有节点认证的注册／心跳接收并绑定实例，不能称作独立的硬件或密码学证明。缺失、无效、过期、伪造实例或旧实例残留的声明不可用于 2.4 放行。

准备、构建、下发、ACK、激活和恢复均重新验证必要的环境／节点／实例／心跳、能力、配置身份和当前安全账本状态；目标冻结后发生节点集合、实例或能力变化则停止并按现有流程重新预览／发布。至少满足现有最小双节点要求，且环境中**全部启用目标**均须符合条件，不因不兼容或离线而静默缩小目标集。节点重启／实例替换须清理或使失效两侧的运行配置确认、安全确认和采集实例状态，旧实例证据不可用于新实例。

### 4.2 版本组合

| 控制面 | 网关 | 预期 |
| --- | --- | --- |
| 旧控制面 | 旧网关 | 保持已有行为，不在本次集成中改变 |
| 新控制面 | 旧网络 2.3 网关 | 非严格环境仍可按主线旧协议发布；不投递 2.4 或要求治理账本的快照 |
| 旧控制面 | 新网关 | 旧控制面不能签发新网关所需的可信兼容状态；受保护请求须保持未就绪／503，不能将缺失字段当成非严格证明 |
| 新控制面 | 新旧混合网关 | 旧协议仅在原有条件下可用；2.4 发布和严格切换须等待所有启用目标具备能力，不能缩减目标 |
| 新控制面 | 全部新网关 | 满足节点、账本、审批、冻结和确认门禁后才可发布 2.4 |

新网关接收 2.4 前须先取得并验证与该环境及当前实例绑定的新鲜安全状态；旧网关即使收到不支持的 2.4 也应拒绝，不应确认成功或覆盖原运行版本。升级顺序采用先完成旧控制面停写／数据库迁移和新控制面切换，再逐个升级网关；不承诺“先升级网关且继续使用旧控制面”无中断。对证据不足的环境，迁移和切换前应在受控入口隔离旧网关，防止它继续使用无法核实的旧配置；无法实施该隔离则停止升级。该组合是目标行为，必须通过真实不同版本组件验证。

### 4.3 发布链路

对预览／冻结、`ReleaseCandidateBuilder`、`SnapshotCompiler`、`PublishCoordinator`、`AckService`、`HistoricalSnapshotService`、`RollbackService`、`ReleaseRecoveryService`、跨环境审批、Gateway `ConfigWatcher`、`SnapshotActivation`、Redis 期望配置及 LKG 恢复逐一复核；不得只修改编译器。继续保留主线交付和跨环境执行、审批、风险确认、锁、审计、Outbox、精确 generation／ACK，以及治理侧的安全账本权限、generation／epoch、节点租约和防降级。

冻结后安全状态、业务资源修订、风险摘要或目标集合发生变化时，拒绝继续并要求重新预览／审批；失败或超时的发布不自动视为成功。快照激活保持原大小、Hash、环境、版本、单调部署序号与持久化校验；2.4 另要求经过签名验证的当前安全 checkpoint 和节点租约匹配。安全状态不完整或不可用时保护性拒绝，而不是继续使用可能更宽松的权限。

### 4.4 回滚与恢复

非严格环境中，在不越过当前安全下限及节点能力的前提下，允许按原流程使用合法的历史 2.0—2.3。严格环境不得直接将网络 2.3 或更弱的历史权限下发为运行状态，也不得回退已确认的安全事件、撤销或高水位。需要回滚业务路由／策略时，读取历史业务配置，叠加**当前**授权、安全账本和下限，生成新的 2.4 冻结候选，并重新经过影响预览、权限和既有审批、全节点发布／ACK；无法证明等价时阻断并明确原因。

LKG 恢复同样检查环境、Hash、协议方言、当前可信安全下限及节点实例；重启后不复用旧进程租约的有效期。安全账本或持久高水位不可验证时，不能以“恢复旧快照”绕过拒绝规则。历史治理 2.3 工件可只读审计；即便来源已证明，直接重投递也必须重新满足全部当前门禁，默认采用上述重建方式。

## 5. 网关链路、授权和统计

保留主线链路顺序：可信代理边界和内部 Header 清理 → 路由 generation → IP → CORS／预检 → 认证及授权 → Transform → 流量策略 → JSON 请求映射 → 缓存 → 熔断 → 重试 → 目标选择。安全账本和租约检查放入认证／授权决策，不得绕过预检既有行为，也不得因路径、查询、Header 或正文变换改变原始授权归属。一次请求使用一致的冻结路由／认证／授权 generation；对并发发布和安全状态变更保留相应的准入锁与单调规则。

覆盖 ApiKey、JWT 和匿名：伪造内部身份 Header 一律清理；无效凭证与已知撤销为 401，授权不通过为 403，安全状态无法确认的受保护请求按合同为 503。CORS 拒绝／预检、IP 拒绝、匿名及 JWT 的行为以主线已有合同和回归为准。重试不重新认证或扩大授权，缓存命中不能绕过认证；安全状态变化后不能通过缓存访问被撤销的资源。适用 JWT 的 Application 映射及 RouteMethod 检查必须覆盖。

主线使用统计和治理凭证安全证明分开：

- 主线指标仍为每个环境中**认证与 API 授权通过次数**和最近使用；后续 429／上游失败、缓存命中各算一次，内部重试不重复；无效、过期、无授权、JWT、匿名和预检不计。原有有界采集、批量去重、迟到处理与 Partial／Gap 可见性保留。
- 治理侧保存带环境、节点、实例、发布序号／Hash、租约及请求完成事实的轮换证明；主线小时汇总不能冒充单实例证明，不能把两条管道的数字相加。轮换所需的每节点成功证明须同时满足认证和授权通过、最终 HTTP 状态为 200—399、无传输失败且客户端未中断；429、上游 5xx、仅认证／授权通过而请求未成功均不能算轮换成功。即使每个网关有成功请求，也不能据此宣称全部消费方已迁移。两种管道各按各自时间点记录，不完整均明确展示。
- 原主线统计采集故障不改变 API 认证结果；若治理证明所依赖的安全状态不可用，则按治理安全准入合同处理。两者故障状态不得混为一谈，实际记录点、持久化容量及恢复须通过测试证明。

## 6. 凭证轮换：手动与正式模式

### 6.1 普通轮换

保留当前主线流程：创建新凭证并一次性展示 Secret；按现有审批流程发布并验证；观察后由有权限管理员**显式**撤销旧工作凭证，再按既有流程发布。不能自动发布、自动撤销、自动延长权限，也不能把统计缺报解释成旧凭证无人使用。保留最后有效凭证影响预览、`If-Match`、风险摘要复验与风险变化 409；Secret 不进入 URL、日志、审计、持久幂等响应或列表，关闭弹窗后不能重新读取。

普通撤销沿用主线现有 `credential.manage`、作用域、影响确认和工作配置语义：原凭证更新接口写入 `Revoked` 只改变工作状态，运行网关以其已发布快照为准，直到该变更按既有审批发布并获得节点确认；不能让治理分支的兼容 PUT 在这一操作中悄悄改成立即安全撤销。治理即时撤销使用独立、明确的 `POST /credentials/{id}/revoke` 及 `credential.revoke` 权限、理由和风险提示；正式轮换中用户已明确确认的撤旧也走即时安全账本。两条操作要在页面区分生效时点。

独立即时撤销在首次提交前同样要求第 6.2 节的完整受控入口前置条件：当前 2.4、所有启用目标的当前实例已确认部署并具备安全账本／租约能力，且旧网关及其他旁路入口已被运维隔离并验证。条件不满足返回明确的 409，不创建或伪称完成即时撤销；管理员可先隔离旧入口并完成升级，或使用普通撤销和既有审批发布流程。接受即时撤销后，账本提交、各节点确认和入口覆盖分别展示；节点故障或目标变化不能抹掉已提交撤销，也不能把部分确认报告为全面生效。平台不能仅凭已登记节点证明平台外的直连入口已关闭，该事实必须由受控部署检查验证。

对 `LegacyGlobal` 凭证，即时撤销不是单环境操作：须在一致性读取和受控锁下，合并当前授权及应用映射、所有相关环境的冻结候选与可核验历史快照，找出可能使用该凭证的全部环境；拒绝调用者只指定某一个环境。历史工件缺失、解析失败或环境范围无法确定时阻断，不将未知环境排除。调用者须拥有所有受影响范围的撤销权限，权限不足时不泄露不可见环境信息。所有仍承载流量的环境都须满足上一段的完整 2.4／节点／入口条件；未运行网关的历史环境只有在可证明入口已隔离、并持久禁止旧节点／旧快照重新提供流量时，才能以“已封存、无运行入口”参与，不要求为一个已封存环境虚构双节点 ACK。无法证明隔离则阻断。

全局撤销事实及其所有受影响环境的账本事件、墓碑、目标和审计必须在同一数据库事务内原子写入；任一环境状态异常不得留下部分环境已提交的假成功。全局撤销后，新增环境、授权、历史候选重试或重新启用封存环境都必须首先继承该撤销事实，采用 2.4 和当前安全状态，不能重新投递可放行旧钥的历史快照。运行环境的当前实例确认与封存环境无入口分别显示，不能将空 ACK 集合当作已执行节点确认；所有实际入口均有匹配证明或已封存后，才可按各自状态汇总结果。

持久模型和迁移须区分“工作状态已撤销”和“安全账本已即时撤销”：普通更新不能仅因工作行的 `Status=Revoked` 而触发全环境安全账本不完整或提前拒绝；安全账本读取／租约签发必须核验所有**即时安全撤销事实**均有完整墓碑，而不能把任意缺失墓碑一概当作正常工作撤销。已有主线库的 `Revoked` 保持原工作含义，按历史已发布快照计算运行状态，不批量伪造成已即时安全撤销；不可根据新表为空抹除既有可信安全撤销。即时撤销一旦记录，任何工作配置、历史快照或回滚均不能使该凭证重新放行。需以明确的持久来源标识、原子写入和数据库访问控制防止绕过；工作状态、各环境已发布状态及即时撤销状态在界面分别展示。

### 6.2 明确选择的正式轮换

正式模式是独立、可见的选择，不替换普通向导；未显式选择并确认自动撤旧的请求不得创建自动撤旧任务。仅支持同环境 `EnvironmentBound` 旧凭证；全局凭证先按现有治理规则迁移，不能暗中转换。**创建前**，环境的当前 2.4 快照必须已发布，全部启用目标（不少于两个）均须是能处理 2.4、安全账本和租约的当前实例，并已确认当前部署、有效安全状态及实例身份；旧网络 2.3 网关、缺失确认或混合节点一律不能启动正式模式。只对平台控制的已登记网关承诺这些规则；外部直连旧网关等旁路须由环境运维隔离并验证，否则不能声称硬截止覆盖全部入口。确认界面显示目标环境、旧凭证掩码、新凭证有效期、重叠窗口、**确切硬截止时间**、全部目标节点、最后有效凭证风险、当前授权／发布状态，以及“即使新凭证尚未验证，硬截止仍会撤销旧凭证，调用可能中断”。明确说明处理器、账本或节点故障导致安全租约无法续签时，同环境依赖安全状态的其他 ApiKey／JWT 请求也可能暂时收到 503；不声称影响只限一把钥匙。

管理员须拥有目标作用域下的轮换与撤销权限，明确勾选并二次提交硬截止自动撤旧确认；服务端要求不可缺省的显式确认值、理由、`If-Match`、幂等键与绑定环境／旧凭证／时间／风险摘要的预览哈希。服务端在同一受控事务内重新验证身份、权限、目标和风险；数据或风险变化返回 409／412 并要求重看，不接受旧客户端通过调用旧接口隐式开启自动撤销。审计记录授权者、时间、范围、目标、截止和风险摘要，不记录密钥材料。

重叠和硬截止遵守环境配置及新旧凭证原有有效期；确认后治理工作配置可将旧凭证有效期缩短到所选硬截止，不自动延长旧权限。页面区分工作配置、已经发布的运行配置、节点确认及安全账本状态。双钥仍需经过既有审批与全目标节点发布；新钥验证须有每个**当前实例**、当前发布与第 5 节所定义的成功请求可信证明，不能拿主线小时统计或上一个实例的记录代替。

轮换期间节点实例更替、增删或状态变化时，旧实例的 ACK／租约／用量证明立即失效；新实例必须先通过 2.4、安全账本、当前发布及安全状态确认才允许进入受控流量。目标变更须审计并重新核对全部当前实例，不得静默缩减撤销目标或沿用旧实例证明；未完成重新验证时不能手动标记验证成功。已经确认的硬截止不会因节点缺席而取消：到期仍发起撤销，未能证明安全状态的受保护入口拒绝请求并显示未完成／部分状态。

管理员可在硬截止前按授权规则显式完成并撤旧；**仅因重叠窗口结束或已验证，不提前自动撤旧**。到达已确认的硬截止后，即使新凭证未验证也由系统发起旧凭证撤销，事务性记录账本／Outbox／审计；已离职或权限变化不追溯改变已确认的截止决定。撤销可能处于待传播或部分确认，页面须显示真实状态，不把“已发起”写成“全部网关已生效”；节点未能证明已实施时按安全租约合同拒绝受保护请求。处理器重启、重复投递和事务重试不得产生多次或互相矛盾的撤销事件。

硬截止的安全承诺是：在约定时钟偏差范围成立时，**截止后不再准入使用旧钥的新请求**；不保证已经准入的请求在截止瞬间被中断，也不承诺处理器或数据库故障时账本事务必定恰在截止时刻提交。正式轮换准备事务以数据库时钟校验：任何已发出的相关节点租约如可能越过“硬截止减最大允许时钟偏差”，则拒绝准备并提示选择更晚时间；后续租约到期时间也必须不晚于该边界。已到边界且撤销事务尚未完成时停止签发会放行受保护请求的租约，节点按本地单调时钟过期，不能借重启、回拨或旧租约延长；时钟偏差超过配置上限或无法证明有效租约时保护性拒绝。

若截止时处理器、数据库或账本不可用，受影响环境的受保护 ApiKey／JWT 请求可能先返回 503；恢复后处理器以幂等方式补记并传播撤销，所有目标确认后才显示已完成。若撤销已提交且安全状态新鲜，旧钥按已撤销返回 401，其他通过认证授权的流量可在租约规则允许时恢复。中止只有在截止前已完全确认时才解除该截止约束。验收必须覆盖截止前后、最大时钟偏差、跨截止旧租约、未完成事务、节点重启与墙钟回拨；不得通过扩大偏差或复用过期租约制造通过。

中止必须在截止前由有权限管理员显式发起，并撤销新钥及等待全部安全目标确认；仅完全中止后取消未来自动撤旧。中止尚未完成而到达硬截止时仍按此前确认的规则保护性撤旧并提示处理。中止不自动恢复已撤销凭证、不自动延长已缩短的旧凭证窗口；若需要调整尚未撤销凭证，使用现有受权限、风险预览和发布约束的显式操作。状态竞争或截止后收到的中止／完成请求必须依据服务端事务时间和修订拒绝或展示已产生的结果。

## 7. 数据迁移与现有数据保护

治理工作区的 22 个迁移主体是未提交草稿，编号均早于主线最近迁移。不能直接覆盖主线 EF 模型快照、重排已应用主线迁移或假设两个版本的迁移集合自然兼容。以主线模型和迁移历史为准，将经审查的治理模型变化生成新的、有序且可追溯的集成迁移；逐项核对列、约束、索引、原始 SQL、默认值、外键、历史账号／凭证及数据语义。旧草稿和历史证据原样留存，不伪造其已执行状态。

采用向后兼容的扩展、受控回填、校验和约束收紧；已有账号密码、角色、范围、凭证及业务记录不重置。对 `LegacyGlobal` 和环境绑定、旧授权、已发布快照、已有统计和迁移中断后的重入分别验证。检测冲突、重复或无法判定的数据时阻断并给出可恢复报告，不自动删除、覆盖、扩大授权或清空表。

自动升级支持的基线是空库，以及迁移历史和实际结构可核实为当前主线或其受支持主线祖先的数据库。治理侧 22 个草稿迁移是否曾应用于任何现存数据库目前未知：如果发现其中任一个迁移 ID、治理专属结构／记录，或者迁移历史与结构不一致，自动升级入口在执行任何迁移或业务写入前必须拒绝并报告；保留原历史和数据，不自行插入／删除 EF 历史记录，也不以改名后的新迁移掩盖旧迁移。此类库的兼容转换不纳入本次自动升级支持范围；如实际发现且需要保留使用，先针对其完整或部分迁移状态建立独立、可验证的转换方案，再单独验收，不能把阻断写成升级通过。

空库初始化、从受支持主线历史升级、失败阻断／修复后重试，以及治理草稿历史／未知历史被阻断，均须在独立 PostgreSQL 验证。EF `MigrateAsync` 入口和交付用独立幂等 SQL 脚本都必须在第一项变更前执行同等历史与结构检查，并分别执行正反测试；现有测试覆盖前者，不能证明带 `DO`／事务控制的 SQL 路径正确。核对升级前后业务行身份、约束、索引、迁移历史、已有数据摘要及两种脚本的最终模型；真实生产数据和原环境不用于试验。扩展支持 2.4 的数据库 `CHECK`、账本读取／比较和所有调用点，同时保留原账本事件、哈希链及签名 checkpoint 的语义。

### 7.1 控制面切换与软件回退边界

数据库执行本次集成迁移前，必须停止并隔离该数据库上所有旧控制面和旧 Worker 写入，完成备份及身份核对后再迁移；不支持旧／新控制面同时对已迁移数据库写入。旧控制面的凭证、授权和安全写路径没有新规则所需的字段与修订，可能违反新约束或绕过账本，不能只依靠页面维护提示。迁移前须以数据库角色和连接隔离确保旧进程无写权限，并验证旧连接的写入确实被拒绝；若旧角色拥有表所有权或超级用户权限，普通 `REVOKE` 不构成有效隔离，须先通过凭据／连接隔离及进程停机提供等效保证，否则停止迁移。迁移后只启动匹配集成版本的控制面／Worker，并验证实际连接身份与写栅栏。

“旧控制面＋新网关”的兼容测试只适用于尚未迁移的旧主线数据库。迁移后若启动旧控制面，应在建立写入前被基础设施拒绝，不支持把旧控制面接回新库作为回退。这里的**软件版本回退**与第 4.4 节的**业务配置回滚**是两件事：一旦升级后产生新安全事件、撤销或业务写入，不能简单恢复旧数据库／旧控制面并丢弃这些变化；优先前向修复。确需恢复时须先停止写入、核对安全高水位及各持久状态，制定单独的数据恢复和防重放方案；无法证明不丢失已生效安全事实则拒绝。本文不授权对现有 4192 等环境执行停机或切换。

以主线固定 SDK `10.0.401` 为起点；治理工作区把它改为 `10.0.402`，不在整合时无条件覆盖。当前主机未发现 `dotnet`，离线可用固定工具、锁定恢复和构建方式仍需核实；不得为了通过验证擅自放宽漏洞审计或下载不受控依赖。

## 8. 隔离集成与验证门禁

1. 固定本设计输入和所选产品文件的原始 Hash，记录 46 个冲突及 3 个新增／新增差异的逐项处置；在独立候选中对照双方语义逐项整合。历史证据、缓存、运行目录、凭据和未审阅文件不进入产品提交。任何上游输入变化都重新评估，不能覆盖原治理工作区。
2. 针对 2.0—2.4、两类 2.3、空／完整／部分治理字段、重复键与大小写、过大负载、历史字节与 Hash、旧版节点和新旧组合编写兼容及拒绝测试。覆盖旧环境证据齐全、缺一项、身份不一致、复验时变化和单调状态转换，以及安全下限从治理 2.3 到 2.4 的含义、旧账本哈希链与签名 checkpoint、撤销墓碑、高水位、断电恢复和 LKG 不降级。
3. 覆盖 ApiKey／JWT／匿名、预检、IP／CORS、Transform 全方向、路径改写与 RouteMethod、内部 Header 伪造、重试／缓存、并发切换、401／403／503、用量记录和缺报。路由修订变化后，旧授权应可留存但拒绝对应请求，重新审批后按新修订放行；无关授权不受影响。验证独立证明与主线统计均只记录各自合同，不重复或跨实例复用。
4. 覆盖普通轮换手动撤旧在审批发布前后分别生效的状态、旧客户端 PUT 不触发即时撤销、独立即时撤销始终不可回滚。全局凭证须覆盖跨环境枚举、历史候选与快照、权限不足、入口未隔离、无节点封存、事务原子性、环境后续启用及禁止空 ACK 假通过。另覆盖未确认时不得建立自动操作、旧／混合节点拒绝正式轮换、全部当前 2.4 节点确认后的准入、风险复验／权限／重复提交、截止前手动完成、验证后的重叠结束不提前撤旧、未验证到硬截止自动撤旧、实例更替及未受控入口阻断、处理中断、部分 ACK、中止竞态、缺报和旧钥到期。验证授权通过后 429／5xx 仍计主线次数但不构成轮换成功；200—399、传输故障、客户端中断分别断言。验证日志／审计／幂等响应不泄漏 Secret。
5. 执行第 7 节的 PostgreSQL 空库／升级／失败、旧治理历史阻断、旧控制面写栅栏与独立 SQL 脚本验证；分别验证旧控制面不能向新网关提供可信租约，以及迁移后拒绝旧控制面写入。随后执行双方适用的后端、前端、SDK、发布、审批、回滚及权限回归。验证至少两个真实独立网关的能力门禁、发布确认、节点替换、账本不可用及恢复；固定输入与实际结果逐项记录。
6. 在 1440px 核查应用详情、轮换、风险提示、用量、审批／发布页面和权限不足／错误状态。使用独立测试账号和数据，不影响原有账号或数据。
7. 使用既有许可范围内的隔离资源开展运行验证；G14／性能诊断中的新 A/B、监听、网络、负载或已有环境操作仍遵循原有单独授权和保护约束。完整门禁全部通过、变更清单和证据可审阅后，才可将通过验证的候选合并至主线；任何未通过项目保持明确未完成，不把历史或局部测试当作本候选的完成证明。
