# 独立持久存储：写满与重启验证计划

> 本计划仅供审阅。当前未批准创建或运行实验；不改变现有环境，不以本地测试结果替代生产验收。

**目标：** 先判断独立虚拟块设备是否能提供真实、持久的容量边界，再判断全部 Docker 恢复目标卷是否确实受该边界约束。

**候选架构：** [UTM 独立 Linux guest + 专用有限虚拟块设备](../specs/2026-11-05-independent-quota-backend-design.md)。使用独立 guest 系统盘、目标盘和 daemon；宿主物理磁盘仍与现有环境共享。已有 OrbStack、4192／4194、其他 VM、现有卷、失败证据及 G14 均不作为实验对象。

**源码身份：** 集成工作区 HEAD `369139df0fde68c8309849038e7f7eb7c58955a1`，含未提交变更。执行前还须固定所有实际参与输入的内容清单，不能仅凭 HEAD 认定版本。当前只读分析得到的 SHA-256：`acceptance-backup.mjs` `dee7d34954bf40cf7079b29c2189d2436c0a1e6e45abac8af77a8c121ea38a0d`；`restore-storage-budget.mjs` `224f8152a7ed1880337fc66ec4fd8838a70eb78825550dccd0cf53b4495ef529`；`docker.mjs` `ab949508d0bd4a84592b0e1295b432b02d6fbae4a8cbc339bc003087e70c5ac7`。它们只限定本次方案分析，不是完整执行输入清单。

## 0. 全局门禁

- 本次是方案准备；创建 VM／虚拟盘、启动 guest、分配或写满空间、关闭／启动 VM、清理均须以固定介质、owner 和资源清单形成具体执行审阅包后另行授权。本计划不要求或授权重启 Mac、OrbStack 或现有服务。
- 不下载、不安装新依赖；须先核验本地可用且获使用许可的 ARM64 Linux 启动介质及所需工具。当前未确认可用介质；本次受限扫描仅覆盖项目内未忽略的指定镜像后缀以及下载、桌面和项目根目录的顶层常见名称，不能排除其他位置、后缀或镜像类型。
- 必须证明 UTM 4.7.5 可按清单将新 VM 和磁盘写入获许可位置，并披露不可避免的注册／缓存写入。不能覆盖或复用任何既有 VM；路径、沙箱权限或影响范围无法确定即阻断。
- 每次尝试使用新 UUID、全新独立 owner 与证据目录；不接管旧资源。以独占创建、文件和父目录持久化保存意图及结果；历史失败、未知状态与资源留存，不自动重试、回滚、删除或替换。清理执行入口仍阻断。
- guest 无网络设备、无宿主目录共享、无宿主 Docker socket、无 USB 直通；只允许经核验的离线只读介质和受控串口。既有虚拟机和其磁盘不作任何操作。
- 受保护的 433 项输入、G14 状态和 main 身份分别于试验前后运行既有保护检查并留存结果；该检查不证明卷内所有数据未变。非预期异常、采集失败或身份不一致保持 `Unknown`；预期的 `ENOSPC` 也必须立即停止写入，仅在字节空间耗尽原因及相应证据均核实后，才可进入已授权的冷关机。

## 1. 限额与身份预审

以下是**单次文件系统试验的初始上限**，不是已分配资源：

| 资源／条件 | 上限或下限 | 验收含义 |
| --- | --- | --- |
| 独立 guest 系统盘 | 8 GiB 上限 | 系统、daemon、运行层及 guest 日志的总外层边界；空间不足则停止，不自动扩容 |
| 独立目标盘 | 512 MiB，即 536,870,912 字节 | guest 可见虚拟块设备的逻辑容量，包含目标文件系统元数据；不限制宿主镜像格式元数据、写时复制、日志等实际物理支出 |
| guest 资源 | 2 vCPU、2 GiB 内存 | 启动前还需证明不会挤占现有环境；当前可用内存尚未核验 |
| 宿主独立证据 | 最多 128 MiB；单项日志最多 8 MiB | 记录与目标盘分离；超过限额或无法持久化时停止 |
| 宿主可用空间 | 预留所有计划最坏支出后仍不少于 20 GiB | 以真实宿主文件系统测量；不得把稀疏文件的逻辑大小当作预留 |
| 写入及观察 | 固定数据块；实际写入总量不超过目标盘大小加一个 1 MiB 探测块；写入最长 300 秒 | 同时采集 write、flush／fsync、errno、字节总量及时间；遇到满盘即停止写入，只有可归因的预期满盘错误可进入已授权的冷关机步骤 |
| VM 冷停及启动 | 正常关机最长 120 秒；再次启动最长 180 秒 | 超时保留状态，不强制关机、不重启共享 UTM／宿主 |

按创建前 G0、格式化前 G1、数据写入前 G2 三道门禁保存以下核对。任何一项不确定时，在该项对应的下一步之前阻断并保留现场；不能要求尚未创建的文件系统提前具有 UUID。

1. **G0：创建前。** 固定新 owner、VM 名称、干净的新建目标路径及其父目录身份，排除符号链接、覆盖、已有文件和跨目录混淆；记录目标磁盘文件、证据目录、受控临时文件、可只读获得的既有 VM 身份基线及 UTM 注册写入范围。路径必须在用户允许范围内；额外位置需要明确授权。UTM 若在创建时生成 VM UUID，创建后须记录实际 UUID 并证明它不在基线中；不能在创建前伪造该值。
2. **G0：创建前。** 确认离线启动介质、Linux 内核、文件系统工具、UTM 程序和可选 Docker 工具／镜像的来源、版本、大小、哈希、许可和信任状态；无可用材料则停止，不联网下载。既有 VM 包只能作已知存在的元数据观察，不能用作介质。试验 A 优先采用经核验的可启动离线系统盘，禁止无人值守安装或自动格式化；如果需要安装并格式化新系统盘，须另行制定该盘的身份核验与授权步骤。
3. **G0 → G1。** 创建前确定无 backing chain 的固定容量磁盘方案、实际预留／同步能力、全部空间支出和持续监测方案；有授权后创建虚拟磁盘，再在任何目标盘格式化前检查文件身份、guest 虚拟容量与宿主实际分配。APFS 稀疏、压缩、快照、克隆、回收或薄置备使保障无法证明时阻断。测量的剩余空间是变化值，文件表面分配量和任一时点空闲量都不足以单独保证底层块已永久预留，任何检查都不宣称独立物理盘。
4. **G0 起持续。** 在创建或分配前启动并验证监测，按 1 秒周期观察宿主剩余空间及自有进程状态。写入控制候选为宿主独占串口发放逐块许可：每次许可最多一个 1 MiB 块，guest 在完成本块写入与必要的同步后才请求下一许可；执行前必须验证通道身份、断连停写、写入者状态及所有受控填充写入路径确实服从该机制。文件系统 journal、磁盘格式元数据、guest 系统盘、Docker daemon／日志和已进入回写的数据未必受此许可控制，须纳入最大空间支出并单独限额与监控；停止发放许可不等于宿主全部写入立即停止。空闲低于 20 GiB 或测量／控制失效时停止发放许可并保留现场；当前块或同步操作仍可能阻塞，无法证实停止则标 `Unknown`，不自动强停 VM 或其他进程。采样不能防止其他进程在两次观察之间消耗空间，剩余风险须记录并在预审时评估。
5. **G1：格式化前。** 固定新 VM 的实际 UUID、新 guest、目标磁盘文件身份与目标块设备 serial／major:minor／逻辑容量的对应关系；证明其与 guest 系统盘及任何已有设备不同。在格式化操作前再次核验身份，只允许处理本次新目标设备，身份变化即阻断。**G2：格式化后、写入前。** 记录文件系统 UUID、挂载 ID、测试路径与该设备的对应关系并复核；文件系统可写容量预期低于虚拟块设备逻辑容量。
6. **G0 建立口径，G1/G2 实测。** 分别记录宿主、guest 系统盘和目标盘的空间口径。产品未来接入时 `freezeRestoreInputs` 的空间测量发生在 guest 的快照目录，要求 `3 × 实际快照字节 + 64 MiB + maxTargetBytes + minHostFreeBytes`；这**不能**替代 macOS 宿主的 20 GiB 保护线。测试初值可用 `maxSnapshotBytes=128 MiB`、`maxTargetBytes=512 MiB`、`minHostFreeBytes=512 MiB`、`minTargetFreeBytes=128 MiB`；该组值仅用于适配器试验，须满足代码校验且重新核算源数据大小。

## 2. 试验 A：文件系统容量与冷启动

**启动条件：** 第 0 节及第 1 节创建前 G0 均有逐项证据；单次执行审阅包已固定新 owner、可启动介质、VM 名称及磁盘路径、操作范围及退出条件，并获得本次执行授权。实际 VM UUID、G1 和 G2 在后续创建后分别核验，不提前伪造。当前状态：`Blocked`。

- [ ] 在新 owner 下创建限额 guest 系统盘和单个 512 MiB 目标盘；保持新旧资源清单及创建前后身份，确保其他设备不可见或只读不可写。完成 G1 并紧邻操作复核后，只在新目标盘建立文件系统；系统盘、现有盘及宿主卷一律不格式化。
- [ ] 格式化后完成 G2，验证设备序列、文件系统 UUID、挂载点、容量和实际写入路径；在目标盘与 guest 系统盘分别建立有界基线标记并 `fsync`，记录内容哈希。将日志输出到独立证据空间，不把唯一结果存到将被写满的盘内。
- [ ] 在目标盘执行真实有界数据写入，排除空洞／压缩测试数据造成的虚假空间占用。记录每次成功字节、实际分配、`fsync`、UID／权限、文件大小限制、文件系统块及 inode 的总量／空闲／可用量和第一个失败结果；额外写入不超过 1 MiB。成功的容量边界必须是可归因于目标盘**字节空间耗尽**的 `ENOSPC` 或等效设备满错误，guest 可见目标块设备逻辑容量始终不超过 512 MiB，并排除 inode 耗尽、用户保留块、其他配额及单文件限制。宿主盘满、进程内存不足、超时或未知错误均不是通过。
- [ ] 在独立证据空间持久记录每个填充文件已成功 `fsync` 的区段、长度、哈希、实际分配及停写时剩余块数；文件数量和证据均有上限。最后一次未成功同步的区段保持 `Unknown`，不得计为已持久化数据。只有证据齐全且满盘原因明确，才可进入已授权的冷关机；监控失效、宿主空间风险或错误归因不明时停止并保留现场，不继续重启。
- [ ] 不删除、截断、回滚或腾挪测试文件。对新 VM 执行正常 guest 关机，确认该 VM 实际停止；只重启同一新 VM。不能以进程重启、暂停／恢复或重启 OrbStack 代替冷停／启动。
- [ ] 重新核验同一虚拟磁盘、guest 设备／文件系统 UUID、挂载及完整基线内容；只读逐项复核所有已成功同步的填充区段长度／哈希、文件分配和目标盘剩余块数，并解释文件系统重挂载造成的合理元数据变化。出现已确认数据丢失、截断、不可解释的分配或空间回退、证据缺失、无法挂载或无法冷启动时保持失败／`Unknown`，不得通过释放测试文件或重置现场取得伪通过。
- [ ] 记录宿主空间和保护检查结果，保存 VM、盘、意图、日志、失败和结果。通过只表示**该设备**的容量与 guest 冷启动观察通过，不证明 Docker 卷、平台恢复、物理宿主重启或生产通过。

## 3. 试验 B：Docker 卷组覆盖

**启动条件：** A 的证据及独立审查通过，且另有可核验的离线 Docker daemon、CLI 和小型固定镜像。B 使用新的 owner、新 VM 和新目标盘，另行形成固定审阅包及执行授权；须对 B 自身重新执行 G0／G1／G2、宿主 watchdog、容量和时限门禁，不复用或修改 A 的失败／成功现场。

- [ ] 启动全新 guest 自有 daemon；目标文件系统在 daemon 访问前挂载到其 `local` 卷根。记录实际 `data-root`、containerd 根、daemon/socket 身份和挂载拓扑；若版本不支持该布局或任何一项未落在限定路径，阻断。
- [ ] 创建两个新 owner 的普通 `local` 具名卷，以非 root 和 root 两种受控写入分别验证：卷 inspect 身份、容器实际挂载、guest mount 设备、UUID 和宿主目标盘是一条对应关系；未确认前不写入。实验容器不使用 `--rm`，退出后及日志均保留。
- [ ] 以两卷合计而非分别 512 MiB 为口径执行受控写入，证明合计空间受同一真实边界限制，留存正常写入及可归因于目标字节空间耗尽的边界失败。记录块与 inode 数、文件限制、非 root 保留块、日志和 Docker 元数据占用，不能把较早的用户空间耗尽误报为精确 512 MiB。
- [ ] 实验自身发现缺失挂载、卷落入系统盘、错误 daemon、目标盘替换、证据不可写或 owner 不匹配时，停止写入并保留现场，不继续重启；此观察不能称为产品初始化／提取阻断已通过。仅在预期字节空间耗尽已归因、监测正常且两卷全部已同步区段的长度／哈希、分配和剩余空间摘要已持久化时，才对同一新 VM 冷停启动并逐项只读复核；daemon 满盘不能启动则如实失败，不清空卷。
- [ ] B 只验证两卷和设备映射，不自动运行产品恢复；所有真实动态卷的完整覆盖和三阶段故障阻断留待第 4 节的产品适配门禁。

## 4. 产品接入及未包含的验收

只有试验 B 的证据与审查通过后，才可以另行设计可信 `storageVerifier`。它必须独立核验真实设备、容量、实际挂载、daemon 和卷身份，并绑定 `preflight` → `before-initialization` → `before-extraction`；同一 `quotaId` 不能遮蔽设备或卷替换。当前接口对 `availableBytes >= quotaBytes + minTargetFreeBytes` 只是数字检查：若将目标文件系统自身的空闲量作为 `availableBytes`，512 MiB 限额加 128 MiB 保留量要求至少 640 MiB，目标设备本身无法满足。后备存储／预留层与该字段的口径尚未证明；产品适配保持 `Blocked`，须先用真实证据定义并验证空间关系，或另行审查接口合同变更，不能人工构造 proof 或缩小限额来绕过。

此后仍需单独准备离线产品源码及全部镜像、可信 provider、按真实 manifest 和 capabilities 确定的完整动态卷清单、三阶段缺失挂载／错误 daemon／身份替换阻断、成功和失败恢复、跨进程身份与锁、source→clone 来源绑定、独立连续性见证、旧写入者隔离及现场复核清理。现有 `reviewed-cleanup` 仍是只读预览，执行函数无条件阻断；不能以本计划解除。恢复代码仍有 `docker/compose run --rm` 一次性容器路径，不能把该入口阻断说成全部自动清理已关闭；未来产品执行审阅包须逐项处理这些路径、明确失败容器及日志的保留方式。已有隔离 PostgreSQL 旧写入者 5/5 结果不代表生产隔离通过。

本计划验证的是同一 guest 的正常冷停／启动；不等于宿主断电、物理主机重启、崩溃一致性或防回滚验证。以上任何新增试验均须单独设计并获得相应授权。
