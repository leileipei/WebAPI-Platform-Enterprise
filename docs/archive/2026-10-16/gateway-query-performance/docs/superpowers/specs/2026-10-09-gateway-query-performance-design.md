## 4. Gateway 设计

### 4.1 索引属于 RuntimeGeneration

从该代已经冻结的数据构建以下查找结构，构建完成后才允许注册和激活：

- Route ID → RuntimeRoute。
- Cluster ID → RuntimeCluster。
- Application ID → RuntimeApplication。
- AccessKey → 同代 Application 与 Credential；使用原有精确字符串比较语义。
- Route ID → 已解析的有效认证配置与用于观测的来源策略。
- JWT 认证策略 ID + 精确 claimValue → Application ID；不同策略之间不得共享映射命名空间。
- Application ID + API ID → 该 API 的全部授权窗口；请求时仍逐个检查该小组内的 ValidFrom/ExpiresAt。

对支持冻结字典的目标运行时使用冻结查找结构，或使用构建后不再修改的私有字典；外部不得获得可变集合。新结构引用同代冻结对象，避免重复复制大型字符串和所有资源数组。

索引中保留过期、未来生效、撤销凭证和停用应用的记录；每次请求仍检查状态与时间。不能在生成时提前删除它们，也不能缓存成功认证结果。JWT 签名、issuer、audience、算法、token 类型、时间窗及 Bearer 转发规则继续使用现有校验器。本批不引入加密对象池或更换验证算法。

### 4.2 生命周期与兼容

- 请求只使用从 YARP 路由 metadata 获得的 deploymentSequence 对应租约；禁止改成读取 `store.Current` 后拼接旧路由。
- 已开始的旧请求继续使用旧代索引。新代失败时保留旧运行代、LKG 与 ACK 行为。
- 索引构建失败按既有配置应用失败路径报告，不形成半注册的新代。已取得的资源须释放。
- 重复 ID、重复 AccessKey、缺失引用及无效映射不能覆盖写入字典；保持 Snapshot 验证的拒绝语义。
- Runtime Snapshot 2.0/2.1/2.2 原字节、哈希及回滚协议不变；索引是内存衍生数据，不序列化进 Snapshot。
- 凭证秘密、哈希、JWT 原文不进入指标标签、SQL 参数日志或公开证据。

## 5. 管理查询设计

### 5.1 通用规则

对已有分页接口统一执行：现有参数规则 → 权限/范围过滤 → 授权结果 Count → 完全排序 → Skip/Take → 页内批量关联 → 现有 DTO。

必须保留：

- `Pagination.Slice` 现有默认页 1、每页 50、页号 1–1,000,000、页大小 1–100 的钳制；不能误套审批收件箱的 422 参数规则。
- Total 只统计可见资源。空页、越界页、空范围的返回结构不变。
- 原排序主键保留，增加 ID 为稳定次排序键；分页固定数据集内不得重复或遗漏。
- 活跃用户、功能权限、组织限定角色、Scope、组织/项目/环境启停、401/403/404/409 行为不变。
- 显式资源查询与集合过滤分别验证；不能以空列表替代应返回的未授权/不存在响应。
- 每个列表请求中权限集合只做请求内预取或 SQL 相关子查询，不增加跨请求权限缓存；后续请求必须看到撤权。
- 不新增“平台管理员自动看全部”的捷径；遵循当前 AuthorizationService 的实际权限与 Scope 组合规则。

Count 与页数据需用同一授权表达式，避免权限重复实现。普通列表保持现有并发可见性；不承诺跨多个请求的快照分页。对安全证明需要同一事务视图的复杂读取沿用/采用有界只读事务，并在计划中列明超时与撤权测试。

### 5.2 核心列表及数据查询预算

2026-10-11 用户明确选择的路由列表例外：`RouteService.ListAsync` 在原环境授权之后，只投影本环境全部 `ID / Path / Priority` 轻量排序键，按原 `RouteNormalizer.MatchOrder` 和 .NET 当前文化路径比较器排序，并补 ID 稳定次序；从同一键集合得到 Total 和页 ID。完整路由字段及有效策略绑定只读取本页，空页不读取这些关联。路由数据 SQL 仍≤4；其读取行量允许包含全部环境排序键，记为 `N + 本页完整数据/绑定 + 权限范围行`，不得再宣称该列表读取行量只随页大小增长。其他列表预算、原字段/权限/状态码、分页钳制和业务流程保持原约束。新增原文化、多语言、等价 Unicode 与 ID 次排序回归，以及仅三列键投影/页内完整记录/空页无关联的真实 PostgreSQL 验证。

预算将“功能权限/祖先 Scope 验证 SQL”和“列表数据 SQL”分开记录。以下上限约束数据 SQL；不得通过把查询改名为权限查询来规避总数记录。

| 列表 | 目标实现 | 数据 SQL 上限/请求 |
|---|---|---:|
| API | 授权项目内 Count + 稳定页查询 | 2 |
| Cluster/Destination | Count + Cluster 页 + 页内 Destination 批量查询 | 3 |
| Route/有效策略 | Count + Route 页 + 绑定/策略批量查询；保留有效认证显示 | 4 |
| Application | 可见性 SQL 过滤 + Count + 页 | 2 |
| Policy | 保留项目策略与组织共享策略规则的可见性查询 + Count + 页 | 2 |
| User/Role | Count + 用户页 + 页内角色 ID 批量查询 | 3 |
| Gateway Node | Count + 页；环境状态在权限/范围读取时批量复用 | 2 |
| Node Event | Count + 页，保持“最近 10,000 条内分页”的 Total | 2 |
| Snapshot 列表 | Count + 页及大小/最新发布联查；不加载 PayloadBytes | 3 |

Release 列表必须保留完整 DTO、冻结候选、审批步骤、目标/ACK、恢复/回滚资格及按权限脱敏的风险信息。使用页内 ID 批量加载相应关联，并复用当前可读 API/版本/Schema 的授权集合；数据 SQL 目标不超过 12 次，不随页内 Release 数量增加。不得把详情字段省略成新 summary DTO 来换取性能。

### 5.3 复杂列表不能遗漏

- 告警事件：授权环境与原筛选放在数据库查询中；Count、事件页、Transition/通知结果按页内 ID 批量读取。数据 SQL 目标不超过 6 次，不随事件页长线性增长。
- 告警规则：保持组织/项目/环境覆盖和目标资源权限判断；批量计算本页规则的预期环境、状态与通知能力。状态判断使用同一数据库时间，不逐规则查询时间。记录状态聚合所读取的本页实际数据量。数据 SQL 目标不超过 10 次，与规则总数解耦。
- 策略引用：Working 使用授权 SQL；FrozenRelease/Runtime 先按真实可读环境筛选、批量获取相关字节，再解析和合并引用。该聚合列表 Total 不能通过先取某一来源的一页再合并得到。保留完整排序、总数和当前 fail-closed 语义；公开测量候选数、解析字节及来源数量。
- 策略引用的写入/删除保护继续检查全部受保护引用，包括当前操作者不可读的资源。列表可见性优化不能缩小写保护的资源集合。

策略引用的数据 SQL 数量允许随本次可见来源批次增长；每批固定至多 200 个资源 ID，禁止逐引用 SQL。先读取 ID 和字节大小，再按合计 8 MiB 的目标预算读取字节；单个合法对象超过 8 MiB 时独立处理，仍受原有合法对象大小限制，不能因批处理预算拒绝原本可读的对象。处理后释放本批 JSON，保留必要的引用摘要，最终精确计算 Total 和排序分页。此处属于有界批处理而非“普通 Count + SQL 分页”，验收单独标记，不能宣称所有聚合已降为固定 2 次查询。

### 5.4 数据库索引

优先复用现有索引，如发布表的 EnvironmentId/CreatedAt/Id。候选新增索引集中于项目 API 排序、环境 Cluster/Route 排序、Destination 的 ClusterId、应用可见范围与排序、策略范围与排序、关联页内 ID。

每个新增索引必须关联优化查询的 `EXPLAIN (ANALYZE, BUFFERS)` 证据；记录小/大规模是否使用、执行时间、扫描行数和额外索引占用。不因关键词存在就给每列盲目增加索引。

新增索引通过正式 EF Migration 管理，测试空库、基线有数据升级及失败后数据完整性。只做增量索引，不改业务字段和凭证内容。已有数据库升级在隔离夹具执行；4192 维护与迁移另列部署操作，不在本设计审阅阶段执行。

### 6.2 数据与场景

|---|---:|---:|---:|---:|---:|
| S | 100 | 10 | 100 | 200 | 8 |

2026-10-09 实施前实际校验发现原 L 档普通快照即达 18,103,978 bytes，超过 16,777,216 bytes 上限；用户明确选择 A，保留 10,000 路由，将 L 档调整为 5,000 应用、10,000 凭证、每应用 8 个授权窗口。原失败证据保留，不提高产品上限。

每 Cluster 2 个 Destination。JWT 使用合法 RS256/ES256 公钥与固定长度请求；每策略最多 128 个应用映射、最多 8 个 JWK，遵循当前限制。按独立策略分组覆盖应用集合；单个策略 Config 仍不超过 32 KiB。所有完整 Snapshot 必须先通过现有验证与字节限制，不能为了跑 L 档放宽产品预算。

管理数据按 S/M/L 档每类 100/1,000/10,000 条资源，分别记录实际总量和可见量。普通列表在固定项目/环境内测量；应用/策略额外覆盖 10 个组织、每组织 5 个项目和每项目 3 个环境的隔离数据。引用/告警/发布按关联数据可验证地生成，不用无效 JSON 占位充数。各列表夹具按场景顺序创建与回收，不要求把所有最大档历史 Snapshot 同时驻留。

数据使用固定 seed、可重现非敏感 ID/排序键；秘密与签名私钥使用本 owner 的临时受限文件。导出脱敏数据规模与业务数据指纹，前后复用同一份有效数据、Snapshot 和请求分布。时间窗和测试时长使合法凭证/token 在两轮测量中保持合法，异常/未来生效/过期窗口单独固定；不通过关闭密码或签名验证提高吞吐。

请求场景独立测量，不能混成一项“网关 QPS”：

1. 匿名匹配与转发。
2. 合法 ApiKey，均匀访问各资源以及固定最前/最末资源。
3. 不存在 AccessKey（401）与秘密错误（401）。
4. 合法 JWT（RS256/ES256），覆盖不同 policy 映射；无映射（401）、无授权（403）另测。
5. 合法凭证但目标 API 无授权或授权窗口过期（403）。

管理列表使用页大小 1/50/100、第一页/中间页/末页/越界页；记录分页排序相等值、Total 和返回 ID。权限身份包含平台角色、组织角色、项目只读、环境只读、无功能权限、无 Scope、停用用户与停用祖先。性能主场景只使用合成的有权账号，负面权限场景独立记录状态码。

### 6.3 测量方法与证据

- 固定基线和优化版本各自从不可变 Git 提交构建；禁止直接打包脏工作区。基准驱动/种子/计数 instrumentation 的哈希也固定并在两轮复用。
- SQL 归类清单作为独立、源码提交绑定、SHA256 固定的审阅证据输入：每个模板关联源码路径、行数和用途说明；最终 B/C 共用同一份清单。初始 B 诊断清单不冒充最终比较输入。保留原始探针计数，归类不删减查询；不明模板继续记未归类。模板采集仅在显式自检中开启，真实 CommandText 保存在 0700/0600 私有目录，不保存参数值；实际性能窗口关闭模板文件采集。
- HTTP 主测：匿名、合法 ApiKey、不存在 AccessKey、合法 RS256 JWT 四种场景在 S/M/L 档均测并发 1/32/128；每个矩阵单元先预热 10 秒，再独立测量 20 秒、重复 3 次，记录重复间的资源状态。ES256、秘密错误、无映射与无授权在 L 档并发 32 补测。主矩阵记录双节点总吞吐和每节点分配；L 档并发 32 另对每个单节点测四个主场景，验证双节点总数没有掩盖单节点差异。
- A/B 与 B/A 顺序交替；相同环境、数据、负载时长和预热策略逐单元对应。所有必测单元都保留完成标记，不能用样本填充缺失单元。按此矩阵预留约 2–3 小时纯网关测量与诊断时间，构建、管理查询和回归另计；这是工作量估算，不是已完成时长。
- 吞吐报告每秒完成请求数，并区分预期状态码、意外失败、超时和未完成请求。P50/P95/P99 来自同一测量窗的完整样本/直方图；保存原始结果，不只导出均值。
- 记录 Gateway/Control Plane 的 GC heap、进程工作集、Docker 峰值/RSS、CPU、GC 分配率与停顿；区分进程内微基准分配与容器整体内存。
- 容器证据来自实际 owner 下运行的 Docker Engine stats 流：内存报告窗内采样峰值，CPU 报告完全位于窗内的区间，cgroup v2 anon/v1 total_rss 单独标识，不混同精确全进程 RSS。就绪等待在测量前完成，不计入吞吐时间；实际 one-off client 身份和限额保留。窗内不足两个点、首尾缺口或间隙超过2500ms时不能关闭基线。参见 [Docker Engine stats API](https://docs.docker.com/reference/api/engine/version/v1.51/) 与 [容器运行指标](https://docs.docker.com/engine/containers/runmetrics/)。
- 另测 RuntimeGeneration 索引构建时间、构建分配、保留旧代且有租约时的双代峰值、退休释放后的稳态内存。不能只测单代稳态而隐去热更新成本。
- 管理查询：每请求 SQL 总数、权限 SQL/数据 SQL 分类、读取行数、响应字节、P95 与分配；采用夹具专用 DbCommandInterceptor 和请求关联计数，读/标量/写命令全部统计。不输出参数、秘密或原始 token。
- `EXPLAIN` 在独立诊断窗执行，不混进 HTTP P95；样本包含每个关键查询的小/大档、实际索引及 buffer 使用。
- 记录负载客户端 CPU、未完成队列和调度延迟；若客户端或后端先饱和，明确标记，结果不能归因于 Gateway 索引。
- 前后改为不同数据库索引时，先在同源逻辑数据的独立恢复夹具应用该版本 Migration，再 ANALYZE；数据库 schema 差异和业务数据指纹分别保存。

输出目录拟为 `docs/evidence/gateway-query-performance/`，包含环境 manifest、前后 source/image/harness/dataset 哈希、矩阵原始结果、对比报告、SQL 计数/计划、权限与分页回归、代切换/回滚验证以及 owner 清理回执。公开文件不得包含管理密码、API Key、Bearer、连接密码、私钥或数据库备份。

## 7. 安全与兼容回归

- 原第 1 包登录限速、失败审计、Redis 故障和全认证模式 Header 清理继续通过。
- ApiKey AccessKey 精确大小写、空/多段输入、重复身份拒绝、应用停用、凭证撤销、未来生效、到期边界、多授权窗口保持一致。
- JWT 策略之间同名 claim 不串用；无效签名/kid/issuer/audience/算法/时间窗口继续拒绝；forwardBearer 原行为不变。
- 双网关切换期间挂起旧请求、凭证轮换、撤权、失败新快照、重复序列、租约释放及旧代回收验证。
- 2.0/2.1/2.2 加载、LKG、历史回滚原字节与哈希保持一致。
- 管理查询权限语义用旧实现结果作为测试 oracle，并增加明确期望断言；同数据下可见 ID/Total/状态码一致，允许原有排序相等项增加稳定 ID 次排序。
- 组织共享策略只有当前授权后代可读；仅环境 Scope 不自动获得父项目资源读权限；跨组织角色不越权；写权限不因列表预取而改变。
- 撤权后的下一请求、只读 Scope、空页、参数钳制、同名排序、事件 10,000 条上限、风险脱敏、告警状态未知/完整判断、损坏可见 Snapshot 的 fail-closed 行为。
- 用户角色批量加载、当前页关联、详情原字段保留；N+1 测试用大于一页的数据验证，不只断言空数据库 SQL 数。

## 8. 完成条件

1. 必测矩阵、环境/数据指纹、前后版本和原始结果齐全；失败/未完成/资源饱和单元有明确标记，未解决则不能关闭本包。
2. 上述权限、分页、Header、JWT/ApiKey、代切换、历史 Snapshot 和回滚回归通过。
3. 普通列表及复杂列表达到第 5 节的数据 SQL 预算，总 SQL 同时报告；请求成本与无关资源总量解耦，不再逐页项授权/关联查询。
4. 大档 Gateway 路由/应用/凭证查找移出请求期全量扫描；授权判断限于目标应用/目标 API 的窗口。微基准明确展示规模增长前后曲线。
5. HTTP 吞吐、P95、内存均有前后对比；不得仅凭理论 O(1) 宣称整体提升。小档出现超过 10% 的中位吞吐或 P95 退化时须查因并复验；大档需有重复可见的查找成本收益。若端到端结果由后端/客户端瓶颈主导，单独报告原因并补测能区分成本的场景，不能删除原结果。
6. 新索引增加的内存、代构建时间和热更新双代峰值透明记录，在既定容器限额内通过加载/回收测试。测得新增稳态内存超过同规模基线 25% 时需逐项说明结构、重复数据与可选收缩；未评估不能关闭。
7. 独立源码审查、必要的完整回归、空库和旧数据 Migration 验证完成，测试 owner 资源归零；实际 4192 未升级须明确标为部署待执行，而非生产验收。

## 9. 交付与实施边界

批准本设计后的实现计划按“基线夹具 → Gateway 索引 → 核心 SQL 分页 → 复杂列表聚合 → 索引/Migration → 前后比较 → 权限安全回归 → 审阅与交付”排序。每个任务给出对应源码、真实测试、SQL 预算及证据命令。

隔离工作区沿用既有项目工作树习惯，主工作区旧文档、截图、部署文件保持原样。不得自动暂存所有文件、丢弃改动或在基准运行中更新既有账号。

本设计不实施 CORS/IP/Transform、首次改密、Credential 使用统计、GitHub CI/签名或新 API 向导，不自动切换 4192。第 2 包的提交、合并、推送和部署按本包后续明确授权与验证结果执行。
